## 2. Network Optimization

### A. Data Transmission

| Factor | Consideration | Optimization Strategy |
|--------|---------------|----------------------|
| **Update Frequency** | Sending position updates at 60Hz consumes bandwidth and server resources. | • Send updates at 10-15Hz for smooth movement with interpolation<br>• Implement variable rate—higher frequency for fast movement, lower for idle<br>• Use delta compression—send only what changed since last update |
| **Message Size** | Large packets increase latency and bandwidth costs. | • Use Protocol Buffers or MessagePack instead of JSON for real-time data<br>• Compress position data to 4 bytes (half-floats) instead of 12 bytes (full floats)<br>• Batch multiple updates into single packets when possible<br>• Implement field-level bit packing for flags and small integers |
| **Interest Management** | Broadcasting every avatar's position to all users doesn't scale. | • Implement spatial partitioning with SignalR groups mapped to grid cells (200m x 200m)<br>• Each user joins only their current cell group and adjacent cell groups in Redis<br>• Use distance-based culling—don't send updates for avatars beyond 300m<br>• Implement awareness limit—maximum 50 avatars per client at any time |
| **Connection Resilience** | Poor network conditions cause disconnections and rubber-banding. | • SignalR handles reconnection automatically via WebSocket fallback chain<br>• Implement client-side prediction with server reconciliation for smooth movement<br>• Implement state synchronization with Redis snapshots every 1-2 seconds<br>• Support connection resumption with session tokens stored in Redis |

### B. API Design

| Factor | Consideration | Optimization Strategy |
|--------|---------------|----------------------|
| **Payload Size** | Large JSON responses increase load times. | • Use sparse fieldsets on REST endpoints—clients specify which fields they need via query params<br>• Use compression (gzip/Brotli) for all API responses<br>• Implement cursor-based pagination for business listings<br>• Cache responses on client with ETags and conditional GET requests |
| **Request Frequency** | Too many API calls overwhelm backend and consume battery. | • Batch recommendations into single endpoint instead of multiple calls<br>• Implement polling with exponential backoff for non-critical data<br>• Use SignalR push for real-time updates instead of client polling<br>• Consolidate mode-change events into a single API call that updates profile and returns fresh recommendations together |
| **Latency** | High round-trip times affect perceived performance. | • Deploy to af-south-1 (Cape Town) as primary region for lowest Nigerian latency<br>• Implement edge caching with CloudFront for static and semi-static responses<br>• Use HTTP/2 for multiplexed requests on REST endpoints<br>• Preload recommendations on mode selection before user begins navigating |
